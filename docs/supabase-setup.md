# Supabase setup for accounts and shared mission planning

ORBITAL COMMAND remains a GitHub Pages site. Supabase provides authentication and PostgreSQL storage. The browser uses the project URL and **publishable** key (or the legacy `anon` key). These values are public in the built website. Never place a `service_role`, secret key, database password or personal access token in the site, GitHub source or browser configuration. Row-level security and the migration below enforce access.

## Required project details

1. Create or open a Supabase project. Obtain its HTTPS project URL (`https://<project-ref>.supabase.co`) and its publishable key from the project API keys page.
2. In Supabase Authentication, enable email/password sign-in and configure email confirmation and delivery for your users. Add the deployed site URL `https://susan-castillo29.github.io/orbital-command/` to the permitted redirect URLs. For local development also permit the exact local URL used by Vite.
3. In the project's SQL Editor, review and run [`supabase/migrations/202611150001_collaboration.sql`](../supabase/migrations/202611150001_collaboration.sql) once. Then run [`supabase/migrations/202611150003_realtime_multiplayer.sql`](../supabase/migrations/202611150003_realtime_multiplayer.sql) to authorise private Realtime channels for team members. Run [`supabase/migrations/202611150002_leaderboard.sql`](../supabase/migrations/202611150002_leaderboard.sql) only if the optional leaderboard is needed. Back up an existing project before applying migrations; do not re-run the table-creation migration. No NASA key is needed.
4. In Supabase **Realtime Settings**, disable **Allow public access** so only authorised private channels can connect. The game creates channels with `private: true`; the migration scopes presence and broadcast reads/writes to authenticated members of the matching team. Supabase Realtime checks RLS policies on `realtime.messages` for these events. [Realtime authorization](https://supabase.com/docs/guides/realtime/authorization) · [Realtime settings](https://supabase.com/docs/guides/realtime/settings).
5. In the GitHub repository's Actions secrets, set `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` to the project URL and **publishable/anon** key. They are passed to the build and will appear in the client bundle, as required by Supabase's browser architecture. They are not substitutes for RLS. Trigger the Pages workflow again after setting secrets.
6. For local development only, copy `.env.example` to `.env.local` and set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`. Restart Vite. The URL must be an HTTPS `<project-ref>.supabase.co` origin; invalid, secret or service-role keys are rejected by the build.

After changing GitHub Actions secrets, re-run the Pages workflow or push a new commit: updating a secret alone does not rebuild an existing Pages deployment. The backend must permit browser requests from the deployed site and the chosen local origin. Supabase's redirect configuration and email rate limits must be checked in the actual project. The project URL and publishable key alone cannot apply migrations or grant administrative access.

## What works

- Email/password registration and sign-in use Supabase Auth. Registration may require email confirmation; actual delivery depends on the project's Auth configuration.
- Sessions are kept in memory for the open tab. Reloading or restoring a backup requires signing in again. This avoids writing the session token to local storage; it does not eliminate the need for XSS prevention.
- A signed-in user can save or restore a private campaign backup. Optional automatic backup runs while the tab remains open after the user explicitly enables it; conflicts disable automatic saving instead of silently overwriting a newer version. Browser storage limits and network failures are reported. The copy includes whitelisted mission progress, designs, resources, scans, reports, the active campaign and campaign archive, not passwords, access tokens, audio settings or the optional local learning assessment.
- A user can create a team, privately share an invitation, join a team, select a responsibility, leave a team and, if owner, rotate invitations or delete the team. Teams admit at most four accounts. Invitation codes are bearer secrets: share them privately and rotate them when needed.
- Team members can share a saved mission design, load it into the existing engineering screen, and share or restore a campaign snapshot in turns. Revision checks reject simultaneous stale writes. The UI refreshes team data approximately every five seconds. Restoring a team campaign replaces this device's local mission data after confirmation.
- Team members use a private Supabase Realtime channel (`orbital-team:<team UUID>`). Presence carries ephemeral player name, role, connection and movement; broadcasts carry the host's selected mission/screen and short team chat messages. The database policies grant channel access only while `auth.uid()` belongs to that team. The existing team membership table still enforces the four-account limit.
- The current solar-system scene and mission exploration scene render visible 3D teammate avatars. WASD/arrows move, Shift runs, E boards/interacts and F triggers an interaction; positions and basic movement/interaction animations are sent through presence. The host's mission destination and main screen are mirrored to other connected members.
- The team centre includes a ready check for every roster member and a host-only mission start. When all roster accounts are online, have a valid role, and are ready, the host broadcasts the selected mission and ship/design; clients show a short launch transition and enter the exploration scene together.

This is an initial **real-time cooperative presence, launch and 3D avatar layer**, not yet a server-authoritative shared flight simulation. Transit time/resource decisions, exploration resources, scans, samples and mission progress still run and save locally on each device; the host's flight physics are not yet the canonical state for every client. There is no team voice chat or competitive matchmaking. Realtime packets are client-generated and are not suitable for anti-cheat or prizes. Personal and team backups are distinct; sharing a campaign exposes its included mission data to all members of that team. Do not use real personal or confidential information as mission data.

## Validation

- `npm test` tests configuration, backup filtering and existing mission systems without production credentials.
- `npm run build` validates the static site. `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` may be omitted, in which case the Teams screen reports that the service is not configured.
- `tests/supabase-rls.sql` tests team privacy, invitation rotation, four-member limit, revision conflicts and campaign isolation. It was run against disposable PostgreSQL with a mocked `auth.uid()`; it is not a substitute for a test against the actual Supabase project.
- `tests/browser-collaboration.cjs` exercises two browser contexts using a mocked Supabase service. Start Vite with `VITE_SUPABASE_URL=https://orbitaltest.supabase.co VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_test npm run dev -- --host 127.0.0.1 --port 4190 --strictPort`, then run `node tests/browser-collaboration.cjs`. The mock does not connect to a real account.
- Before inviting real users, test confirmation emails, two real accounts, the four-person limit, private backups, role changes, stale-write conflicts, revocation, restoration, cross-device behaviour, rate limits and RLS in the actual project. Review storage, backups, retention, account recovery and security monitoring for the expected deployment.

## Global leaderboard and explorer diploma

Run [`supabase/migrations/202611150002_leaderboard.sql`](../supabase/migrations/202611150002_leaderboard.sql) after the collaboration migration to enable the optional top ten. New registrations request a username, first name and first surname; existing users can complete these in Teams. A player must save a private campaign backup before choosing to publish. The public leaderboard displays those profile fields and XP; participation can be withdrawn. Profile changes appear after publishing again. Never place sensitive information in the public name fields.

The ranking reads XP from the player's saved campaign. The current simulation runs client-side, so these scores are **player-reported and unverified**, not suitable for prizes, trusted competitions or anti-cheat decisions. The printable diploma is available only in the game after a complete campaign, or from a completed campaign record; it is an in-game recognition, not an independently verified credential.

Run `tests/supabase-leaderboard.sql` after both migrations in a disposable PostgreSQL database with a mocked Supabase auth schema. This does not replace integration tests with real accounts and the production RLS configuration.
